# 2026-10-10 — Brand/organisation files up to 100 MB, streamed to disk (Csilla)

**Decision (Csilla, 2026-10-10).** The upload limit for brand/organisation files (logo, brand manual, reference, document — PDF too) goes
from 10 MB to **100 MB**. Fonts stay **10 MB** (`BETU_MAX_MERET_BAJT`); post images stay **10 MB** (`KEP_MAX_MERET_BAJT`, new constant,
same value as before). Trigger: Szente 09-16 „can't upload a larger file, a PDF” (triage (d), Round 3).

**For Vilmos — information only (Csilla decides, he is not asked).** This touches the upload path. What did NOT change: authentication
(`kapu(…, "szerkeszto")` first, before any byte is read), the role rule (viewers 403), the content-based type check (first bytes, not the
name or the header) and the SVG ban, tenant scoping (the store writes under the organisation's folder and the row goes in through
`szervezetKent`, RLS as before; another organisation gets 404). What changed: a bigger body is accepted on ONE route
(`/api/arculat/fajl`), and it is written to a temp file before it is checked. The temp file is in `FAJL_MAPPA/_feltoltes/` (mode 600,
random name, `wx` flag), deleted on every error path, renamed into place on success.

## How it is built (why it is safe on a 16 GB NAS with no headroom)

- `apps/web/fajl/beolvas.ts` `torzsFajlba`: reads the request body chunk by chunk into the temp file with a running byte count; above
  the limit it stops at once, deletes the temp file and answers 413 `TUL_NAGY` (the existing friendly error). Only the first 512 bytes
  are kept in memory, for type detection. No full-file buffer.
- `packages/fajl-core` 0.3.0: `celMaxMeret(cel)` (100 / 10 / 10 MB), `feltoltFajlbol` (same rules on size + head; the store's optional
  `mentFajlbol` port moves the file into place), `fajlFolyam` + optional `olvasFolyam` port (download as a stream). Old hosts still work
  (both ports are optional; without `mentFajlbol` a big upload is refused, it never falls back to memory).
- Downloads (`/api/arculat/fajl/[id]`) stream from disk with `content-length` (before: the whole file in memory, copied once more).
- Fonts and post images stay in memory (fontkit needs the bytes) but are read with a hard cap (`korlatosBeolvas`), also without
  `content-length` (chunked).
- Places that read stored files into memory now check the metadata first: the image logo is loaded only if ≤ 2 MB
  (`KEP_LOGO_MAX_BAJT`, unchanged), custom fonts only if the file's purpose really is `betu`. A 100 MB logo is stored and downloadable
  but never loaded into the image maker.
- Before answering 413 the rest of the body is read and discarded (up to 128 MB, no memory): measured locally, answering mid-body made
  the client see `ECONNRESET` instead of the friendly message.

**Memory, measured locally** (production build, `/proc/<pid>/status` VmRSS polled every 20 ms, one 99 MB PDF upload then its download,
fresh process):

| | upload peak above baseline | download peak above baseline |
|---|---|---|
| old code, only the limit raised (`arrayBuffer()`) | **+344 MB** | **+443 MB** |
| this branch (streamed) | **+47 MB** | **+45 MB** |

The app container's `mem_limit` is 512 MB (`nas/docker-compose.yml`) — the old path would have been killed by one 99 MB upload. A second
run on the final build (warm process, baseline 384 MB) showed no growth above baseline.

**Tests.** `packages/fajl-core/probak/nagy-feltoltes.proba.ts` (limits, `feltoltFajlbol`, `fajlFolyam`; 55/55 in the package).
`apps/web/probak/nagy-feltoltes.proba.ts` (live): 3 MB PDF 201 and byte-identical download; 99 MB 201, download 99 MB, no temp file
left; 101 MB 413 `TUL_NAGY` with and without `content-length`; SVG 415; font 11 MB 413; post image 11 MB 413; viewer 403; another

**Labels (migration 0160).** New `fajl.hiba_tul_nagy_100`, `arculat_fajl.nagy_mit_100`, `arculat_fajl.halozat_mit_100`; changed

## nginx and the deploy robot — needs one manual step

`nas/nginx.conf`: the server-wide `client_max_body_size 12m` stays; only `location = /api/arculat/fajl` gets `105m` (so a 101 MB file still
reaches the code and gets the friendly 413, not nginx's bare one), with 300 s proxy timeouts.

**The robot does NOT apply nginx.conf changes** (measured in `nas/kirak-sha.sh:85` and `:110`): it copies the new file as `nginx.conf.uj`,
then `mv nginx.conf.uj nginx.conf` and `docker compose up -d --no-build`. The web container's image (`nginx:alpine`) does not change, so
compose does not recreate it, and the single-file bind mount keeps pointing at the OLD inode — the old config stays live, even after an
`nginx -s reload`. (The manual `nas/kirak.sh` recreates web by renaming the old container; the robot path does not.) What applies it, on the
NAS after the robot has deployed this commit:

    cd /volume2/docker/aitmetica-saas && sudo docker compose up -d --no-build --force-recreate web
    sudo docker exec aitmetica-saas-web grep -n client_max_body_size /etc/nginx/conf.d/default.conf

The second line must show both `12m` and `105m`. Until then uploads above 12 MB get nginx's bare 413 (the page shows the „did not arrive
— at most 100 MB” network text).

## DSM reverse proxy — check, don't touch

DSM's reverse proxy in front (Let's Encrypt, → `127.0.0.1:8400`) may have its own body limit. Read-only check on the NAS:

    sudo grep -rn client_max_body_size /etc/nginx/ /usr/local/etc/nginx/ 2>/dev/null

and the practical test after the recreate: upload a ~50 MB PDF on https://saas.mediapartizan.ro in „Minták, kézikönyv”. A JSON 201 means
the whole chain is fine; an HTML 413 page (not our friendly text) means DSM cuts it — that is a DSM setting, Vilmos's area, not changed here.

## Not changed

- `apps/referencia-host` (A-12 second host) still reads uploads into memory, but nginx allows only GET/HEAD on `/referencia/` (read-only
  public demo), so no upload reaches it from outside.
- Disk: a 100 MB upload briefly needs 100 MB in `FAJL_MAPPA/_feltoltes/` (same volume as the file store, so the final move is a rename).
