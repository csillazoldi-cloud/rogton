## The hub write path — NOT determined (closed 2026-10-09 07:53: hub retired as a target, see the update above)

Searched: the repo, docs/, HANDOFF.md, the project docs. Nothing describes how the Project Hub accepts writes from a program.
What is known: the hub is reachable from Claude sessions as the "My projects" tool set, whose `post_feedback(slug, text)` takes
exactly a slug and a text; its state file lives on the NAS share (`/Volumes/Transzmozaik/hub/projects/kommunikacios-munkater/state.md`
on a Mac). Neither tells how a container on the NAS can write to it, or what the key looks like.

So the sender is **pluggable** and **switched off**: `hubKuld()` would POST `{"slug","text"}` as JSON to `HUB_FEEDBACK_URL` with
`Authorization: Bearer <HUB_WRITE_KEY>`. While either variable is empty, nothing leaves the app and the items wait (the marker does
not move, so the first real digest carries them — or only the last 24 hours if there is no marker yet). Writing files into the
hub's folder on the share was **not** built: the hub's file format and locking are unknown, and a wrong write could corrupt
everyone's state.md.

**Question for Csilla/Vilmos:** what is the Project Hub's write endpoint for feedback (URL reachable from the NAS app container,
and the exact auth header), or, if the hub only exists as an MCP server, which endpoint/key should the app use? If the answer is
not "POST JSON {slug,text} with a Bearer key", only `hubKuld()` changes.

## Secrets delivery

`tools/titok/` (README there): the token goes Mac vault → `csilla@Gigabyte` (ssh stdin) → `sudo` → the robot user `gigabyte`
→ the NAS through the robot's `nas/nas-parancs.sh` (the deploy channel). Dry run first, then `--irj`. NAS `.env` backed up
(`.env.elotte-c7-<time>`), edited in place (owner and mode kept), masked diff shown, idempotent. No container restart: the
deploy of this branch recreates the app container because its compose environment changed.

**Robot messages:** `tools/gigabyte-robot/uzenet.sh` reads `~/.config/gigabyte-robot/telegram` with two lines `TOKEN=<token>`
and `CHAT=<id>` (regex: token `[A-Za-z0-9:_-]+`, chat an optional `-` plus digits — a group id works). No code change. The
helper writes `CHAT=-5557911968`, so **deploy/heartbeat messages go to the team group too** (Kati sees them). If Csilla wants
them private, change the `CHAT=` line to her own chat id (the uzenet.sh comment still says "Csilla's chat id").
