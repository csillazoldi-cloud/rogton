## G6 — the chosen design: the app lives in the WARP container's network namespace

```
gma-web ──▶ egress:3000 ─┐ (same namespace)
                         gma-app ── db, kepgyar (docker subnet 172.16.0.0/12, excluded from WARP)
                         gma-egress: WARP tunnel ──▶ Cloudflare ──▶ internet   (everything else)
                         nft kill-switch: no other way out
```

- **How it is wired.**
  - `gma-egress` runs `caomingjun/warp:2026.7.1377.0-2.12.0`: the official WARP client plus GOST, with registration done by the image's own entrypoint.
  - `gma-app` has `network_mode: "service:egress"` and no network of its own. Every outbound request (RSS, user-added URLs, website research, OpenAI, logo fetches) leaves through the WARP tunnel without a code change.
  - gma-web reaches the app as `egress:3000`. nginx resolves that name at request time through Docker's DNS.
- **Why not the proxy design.**
  - The app uses Node's native `fetch` everywhere: `letolto`, OpenAI, onboarding, logo. That would need `NODE_USE_ENV_PROXY=1` or a global undici dispatcher.
  - Worse: `letolto` resolves every host with `dns.lookup` first, as its SSRF guard. On a Docker `internal` network external names do not resolve, so the app would have to keep a route to the internet, and with it a way to leak.
  - The shared-namespace design needs no app change and has no second path.
- **Docker subnets.** Consumer WARP's default split tunnel excludes the private ranges, including 172.16.0.0/12. Traffic to db, kepgyar and the replies to gma-web therefore stays on the docker bridge. This is ASSUMED; the G6 probe checks it with `getent hosts db` and the health check.
- **DNS.** The wrapper switches WARP to `tunnel_only` mode, so WARP does not replace the resolver and the app keeps Docker's 127.0.0.11. That is how it finds `db` and `kepgyar`.
  - Name lookups for outside hosts go from the host's resolver to the ISP. This exposes the queried domain to the ISP's resolver, never the office IP to the target site. Accepted.
  - If `tunnel_only` is refused by the client, the probe shows it (`getent hosts db` fails), and the fallback is to drop the mode switch and test the default `warp` mode.

### Kill-switch — why nothing can leak from the office IP

1. **Egress container stopped or re-created.**
   - The app's namespace disappears with it: the app has no interface but `lo`, so outbound fails and so does inbound (502).
   - `kirak.sh` checks on every 2-minute tick that `gma-app` sits in the *current* egress namespace, and re-creates it if not. Downtime is at most about 2 minutes, and it fails closed.
2. **Container running, WARP disconnected.**
   - The namespace carries an nftables table (`uzem/egress/kerites-belul.nft`, output policy **drop**). It is loaded by the wrapper *before* WARP starts.
   - Allowed out:
     - `lo` (Docker DNS)
     - established/related replies
     - the docker subnets (172.16.0.0/12)
     - anything routed into the `CloudflareWARP` interface
     - WARP's own traffic to the WARP endpoint/API ranges 162.159.192.0/22, 162.159.198.0/23 and 162.159.136.0/22
   - A request to any other address is dropped.
   - The ranges are ASSUMED (taken from Cloudflare's published WARP endpoints). If they are too narrow, WARP cannot connect and everything fails **closed**. If one of them also hosts an unrelated Cloudflare site, a request to *that* site could still go direct while WARP is down. The probe measures the real endpoint with `ss -tunp`.
3. **The host fence** (`uzem/kerites.sh`, root, `gma-kerites.service`).
   - Forwarded traffic from the gma subnets may not reach the office LAN 192.168.1.0/24, Tailscale 100.64.0.0/10, or other docker networks in 172.16.0.0/12; only their own subnets.
   - The gma containers may not open connections to the host itself (its LAN/Tailscale addresses, the other projects' ports).
   - Own chains `GMA-KERITES` (from DOCKER-USER) and `GMA-KERITES-BE` (from INPUT), idempotent, `--torol` removes them. Re-applied at boot and whenever docker.service restarts (PartOf).
   - Measured in the sandbox against a real Docker daemon: two runs → one jump each, all rules present; `--torol` → nothing left. See `plan-out/kerites-proba.txt` in the build report.

### Healthcheck

`gma-egress` has a Docker healthcheck: through WARP, `https://www.cloudflare.com/cdn-cgi/trace` must say `warp=on` or `warp=plus`, checked every 60 s.
- The old "no HEALTHCHECK" rule was for the NAS. The Gigabyte has headroom, and this check is a single curl a minute.
- The app depends on egress with `condition: service_started`, not `service_healthy`. If WARP is down the site still serves pages, and only outbound fetches fail (closed).
- After every deploy, `kirak.sh` step 9 checks `warp=` and exits with code 10 if it is not `on`/`plus`.

## G7 — Cloudflare Tunnel as a compose service

- **`gma-tunnel`** runs `cloudflare/cloudflared:2026.10.0` (`tunnel --no-autoupdate --loglevel warn run`) on `gma-kimeno`. It dials out to Cloudflare only and opens no port.
  - The token is read from the `TUNNEL_TOKEN` environment variable (cloudflared's own variable), filled from `CF_TUNNEL_TOKEN` in the .env. That keeps it out of the process command line.
  - It is behind the compose profile `tunnel` (`COMPOSE_PROFILES=tunnel` in the .env), so the stack keeps running until the token exists.
- **Real client address.**
  - nginx trusts `CF-Connecting-IP` only from 172.16.0.0/12 (cloudflared is a container), then **overwrites** `X-Forwarded-For` with `$remote_addr`.
  - The app therefore sees exactly one trusted address: `MEGBIZHATO_PROXY_DB=1`. Measure it after go-live on `/api/belso/cim`: "ahogy_latjuk" must be your public address, not 172.x.
  - Local requests (SSH tunnel, deploy health check) have no such header and keep their own address.
- **Restarts.** A normal deploy does not restart `gma-egress` or `gma-tunnel`. `compose up` re-creates a container only when its config changed, and the egress script files are compared byte by byte (`cmp`) before they are replaced. Re-creating egress is followed by re-creating the app.
