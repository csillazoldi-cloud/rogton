# 2026-10-18 · G9 — the site gate („kapu”) instead of Cloudflare Access

**Decision (Csilla, 2026-10-18 16:05):** Cloudflare Access is removed. The app itself puts ONE shared password in front of
everything. Brief: `plan-out/G9-FELADAT.md`. Branch `g9-kapu`, built on `g8-uzem` (merge G8 first).

## What it does

- `KAPU_JELSZO` in `~/gma/.env` (never in the repo). Set → the gate is ON. Every request without a valid `rogton_kapu` cookie gets
  the gate page (pages: HTTP 200, the address bar keeps the asked URL, and after the password the visitor lands there) or
  `401 {"hiba":"kapu"}` (API routes and any non-GET request — so a server action or a form post cannot slip through).
- Free without the password: `/kapu` (page + its POST), `/api/egeszseg`, `/manifest.webmanifest`, `/favicon.ico`, `/r18/ikon/*`,
  `/_next/static/*`, `/betuk/*`. On these the root layout passes ONLY the `kapu.*` labels to the browser and looks up no account —
  so nothing about the product (labels, menus, organisation data) is in the gate page or in a 404 under a free prefix. What a
  stranger can see: the » + Rögtön mark, „Jelszó”, „Belépés”, the manifest (name Rögtön + icons) and the static JS/CSS bundles.
- Where: `apps/web/proxy.ts` — Next 16 renamed middleware to *proxy* (Node runtime, so it reaches the database). Rules in
  `apps/web/oldalkapu/szabaly.ts` (pure, unit-tested), tickets in `apps/web/oldalkapu/jegy.ts`, page `apps/web/app/kapu/`.

## One path skips the proxy: the big brand-file upload

Next copies every request body into memory before the proxy runs and passes it on TRUNCATED above `proxyClientMaxBodySize`
(default 10 MB) — measured: the 94 MB upload arrived cut, the 101 MB one got 201 instead of 413. So: the limit is 12 MB (nginx's
normal limit; the code's own friendly 413s at 10 MB keep working), and the matcher skips exactly `/api/arculat/fajl` (nginx lets
100 MB through there, the code streams it to disk). That route asks the gate itself, first thing, before touching the body
(`apps/web/oldalkapu/utvonal.ts`, the same decision function and the same 401/503 answers). Measured with the gate on: 30 MB with
the cookie → 201 and the right size; without the cookie → 401 `{"hiba":"kapu"}`.

## The cookie: an opaque ticket in a tiny table (not a stateless HMAC)

Chosen as the brief preferred: `kapu_jegy` (migration 0185) holds the SHA-256 of a random 32-byte ticket (the ticket itself is
nowhere on the server), the password's HMAC, created / expires (30 days) / last used (written at most hourly) and a truncated
HMAC of the address. Consequences:
- **Revoke every device:** `TRUNCATE kapu_jegy` (Runbook). Takes effect within 60 s (each process remembers a verified ticket for
  60 s, so images and data requests do not each hit the database).
- **Changing `KAPU_JELSZO` invalidates every cookie**: a ticket carries the hash of the password it was issued under; the lookup
  matches on the current one. (Changing the password also needs `up -d app`, which restarts the process and clears the 60 s memory.)
- Cookie: `HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=2592000`. Secure always — the live site is HTTPS at Cloudflare and
  nginx sends `X-Forwarded-Proto: https`. Expired tickets are removed when a new one is issued (short-lived access tokens, like
  expired sessions — not data; the attempt log stays).

## Rate limit: the existing login-attempt log

`belepesi_kiserlet` with a new kind `kapu` (the `fajta` column is plain text, no constraint): **5 wrong passwords per 15 minutes per
address → 429** „Túl sok próbálkozás. Próbáld 15 perc múlva.” — checked BEFORE the password, so the 6th attempt is refused even
with the right password (same rule as the app login). The address comes from the same trusted-proxy logic as the login limit
(nginx overwrites X-Forwarded-For with CF-Connecting-IP; `MEGBIZHATO_PROXY_DB=1`, measured live in G7). The password is never
logged; the log row has no e-mail. The Cloudflare WAF rule (10 POST /kapu per 10 s per IP → block 1 min) is only a backstop.

## Status codes on the POST, and why the proxy fetches its own page

Wrong password → 401 with the gate page and „Nem jó a jelszó.”; rate-limited → 429 with the page. Next does NOT carry a status
set on a proxy rewrite to the rendered page (measured in `next/dist/server/lib/router-utils/resolve-routes.js`: the rewrite
branch returns no `statusCode`), so the proxy fetches `/kapu?h=…` from its own process (`127.0.0.1:$PORT`, inside the app's
network namespace — the WARP kill-switch allows loopback) and returns that HTML with 401/429. If that fails, it falls back to a
303 to the same page (the visitor sees the same thing, only the code is 200). Success → 303 to the page they asked for (only a
local path; `//host`, absolute URLs and `/kapu` itself fall back to `/`).

## Gate OFF (no password) fails open only from the box itself

Empty `KAPU_JELSZO` = gate off, so local development and the ~1100 tests run unchanged. But a live box that lost its password must
not fall open to the internet: with the gate off, a request is let through ONLY if it carries no `CF-Connecting-IP`. The box's one
public path is the Cloudflare tunnel, and Cloudflare sets that header on every request (overwriting any value the visitor sends —
it cannot be removed). So without it a request came from the box itself (127.0.0.1:8410, the SSH tunnel, the deploy's health check
and crawl) or from a developer machine with no Cloudflare at all. The address (X-Forwarded-For) is deliberately NOT the criterion:
the test suite varies it on purpose (rate-limit tests), and Next's proxy does not expose the socket address. Everything coming
through Cloudflare gets „A belépés most nem elérhető.” (page) or 503 `{"hiba":"kapu_nincs_beallitva"}` (API). The health check
stays open either way. (First self-test used the address as well and broke ~50 tests that send their own X-Forwarded-For —
measured, then changed to the header-only rule.)

## Open registration stays — the gate is what closes it

The app's own login and registration work as before once the gate is passed. Registration stays open on purpose (D-17); the gate
is what keeps strangers out of it. Anyone who has the gate password can create an account — share the password accordingly, and
change it (+ `TRUNCATE kapu_jegy`) when someone should lose access.
