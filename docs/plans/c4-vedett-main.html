Protect main: check first, then deploy

Hub chunk c4 · plan for Csilla · 2026-10-06 · full plan: docs/plans/c4-vedett-main.md

Why

  • Today the robot fetches main three times per deploy, so one version gets checked, another built, another's files shipped. That is the 09-21 mix-up.
  • A failed deploy is never retried and nobody is told. That fits 09-22.
  • The robot most likely runs no checks at all today. To be measured first.

Biggest risks

  • Tests delete rows. They will only run against a throwaway database that the robot creates itself.
  • A migration can't be undone. It only runs after the checks pass, with a backup first.
  • Too strict a gate would block every deploy. A written list of the 19 known failures, each with a reason, prevents that.
